# zs500 — ZS500 Heat Pump Protocol

**Python system name:** `"zs500"`
**Wire device type:** `"zs500"`
**Protocol family:** AWS IoT Device Shadow (MQTT for the live device-detail/home screen; a signed REST shadow GET is also used by the systems-list screen for its online/offline badge — see Real-Time Transport below)
**Auth:** See [client.md](../client.md)

---

## Overview

The ZS500 heat pump shares its entire reference (Android app) implementation with the generic "HPM" (Heat Pump Module) device family. There is no ZS500-specific model class, view, or view-model in the reference app — `"hpm"` and `"zs500"` are two distinct wire `device_type` strings that are both routed to the same shared model and handler code. The only places the app distinguishes ZS500 from generic HPM are:

- A device-type string check (`deviceType` containing `"zs500"`, case-insensitive) that gates UI-visible behavior: showing the "Smart" mode option, dividing certain sensor/setpoint values by 10 before display, and showing standby-reason text regardless of firmware version.
- A dedicated BLE GATT device type/packet format used during WiFi provisioning; its Service/RX/TX UUID *values* are shared with another device type (but its packet framing is not, and its Profile UUID is unique) — see BLE Provisioning section.

All status reads and control writes for the device-detail **home screen** and equipment settings go over the **AWS IoT MQTT shadow** — the app subscribes to and publishes on a per-serial shadow topic; this is MQTT-only, confirmed with no REST fallback for that screen. REST endpoints on the shadow host are used in three other situations, none of which is the live home screen: (1) the **systems list** screen (the tile/card view shown before opening a specific device) does a one-shot signed `GET /devices/v2/{serial}/shadow` to read `aws.status` for its online/offline badge — this is a real REST "get current status" call site, just not the one used once you're inside the device's own screen; (2) during WiFi/BLE provisioning, before the device has an active MQTT session, to confirm the device has come online and (for the `shadow` endpoint's GET variant only) to read its aux configuration; and (3) aux-configuration read/write via `systemSetup?key=service`, called from the **Equipment Settings** and **Aux Setup** screens post-provisioning — gated behind a preference flag the app sets to true only for `zs500` (plain HPM reads/writes aux over MQTT instead, via the shadow's top-level `ty` field). OTA status polling and declared service-contact-info (`systemSetup`) calls exist in the Retrofit interface but have no call site reachable for this device type in this app version (see Endpoint Inventory below).

## Temperature Encoding

**This is device-type-gated, not a blanket "HPM family" behavior.** The reference UI code divides `tsp` (setpoint), `sns_1.value` (pool/water temperature), and `sns_2.value` (air temperature) by 10 **only when the device type string is ZS500**. For non-ZS500 HPM devices, the same wire fields are used unscaled (no division). The write path mirrors this: the setpoint is multiplied by 10 before being posted **only** for ZS500.

Confirmed bounds (from the UI's allowed-range check, same min/max for slider clamp regardless of device type): minimum 15.0, maximum 32.0, in the unit the UI displays (post-scaling for ZS500 — i.e. 15.0–32.0 represents °C after the ÷10 step, corresponding to wire values 150.0–320.0 for ZS500 specifically). Whether the device always reports in this encoding regardless of a user's configured display unit (°C vs °F) was not observed in the reference — no unit-conversion logic was found in the HPM/ZS500 view-model code.

---

## Compressor Speed Display

`cmprSpd` is not divided/scaled — it is used directly as a percentage (0–100). Reference UI thresholds for visual indicator segments: `> 75` = all three segments lit, `51–75` = two segments, `1–50` = one segment, `<= 0` = no segments lit.

## Signature / HMAC Mechanics (`signature` query parameter)

Confirmed directly from the reference signing helper:

- **Algorithm:** HMAC-SHA1.
- **Key:** a per-environment API secret key (the same secret used for other signed endpoints across the app; not specific to ZS500).
- **Canonical string:** `{first_argument}.toUpperCase() + "," + {second_argument}`, with no additional query-parameter segment appended when no extra params are supplied (the helper supports appending sorted `key=value&...` pairs after a second comma, but the two ZS500/HPM call sites observed pass an empty map).
- **Output encoding:** lowercase **hexadecimal** digest string (not Base64).

At the three confirmed ZS500/HPM call sites (WiFi-provisioning shadow-status check, provisioning aux-details fetch, and the systems-list online/offline status poll), the arguments passed are:
- First argument: the device serial number.
- Second argument: the numeric user ID (`String.valueOf(userId)`), **not** an HTTP method name or timestamp.

So concretely: `signature = hex(HMAC-SHA1(key = api_secret_key, message = "{SERIAL_UPPERCASE},{userId}"))`.

This differs from a generic "HTTP method + URL + query params" signing scheme that exists elsewhere in the app's signing helper (used by other endpoints) — the ZS500/HPM shadow-signature call sites specifically use `serial` and `userId` as the two components, with an empty extra-params map.

## Real-Time Transport (MQTT)

The reference Android app's transport for the **live device-detail home screen** is the AWS IoT device shadow over MQTT, confirmed with no REST fallback for that screen specifically. The *systems-list* screen (shown before opening a device) is a separate, REST-only status poll (see Endpoint Inventory above) — it is not part of the MQTT flow described here.

**MQTT broker:** `a1zi08qpbrtjyq-ats.iot.us-east-1.amazonaws.com`

**Topic patterns** (serial-scoped), confirmed directly from the reference's MQTT device manager:

| Operation | Topic |
|---|---|
| Request full shadow | `$aws/things/{serial}/shadow/get` (publish, empty payload) |
| Receive full shadow | `$aws/things/{serial}/shadow/get/accepted` (subscribe) |
| Receive update confirmation | `$aws/things/{serial}/shadow/update/accepted` (subscribe) — **not** a delta-update channel; an earlier draft of this document mislabeled it as one. The app's actual flow is: subscribe to `get/accepted` → publish `get` → receive the full shadow → unsubscribe from `get/accepted` → subscribe to `update/accepted` for the rest of the session, merging each update into its own cached copy client-side. |
| Post desired state | `$aws/things/{serial}/shadow/update` (publish; payload is the bare `{"state":{"desired": {...}}}` shape used by the REST write, per the correction above) |
| OTA status/trigger | `events/iaqualink/{deviceType}/{serial}` — used for ZS500's OTA flow; the OTA trigger itself publishes `{"state":{"desired":{"jobId": ...}}}` to `shadow/update` |

`$aws/things/{serial}/shadow/update/documents` and `/update/delta` do not appear anywhere in the reference source — confirmed absent, not just unconfirmed. Any client subscribing to them (e.g. for push-based live updates without re-fetching the full shadow) is relying on generic, AWS-documented Device Shadow service behavior, not reference-app-observed behavior.

**Device-type routing:** the reference's central MQTT message router dispatches incoming shadow messages by the connected device's `device_type` string. Both `"hpm"` and `"zs500"` device types are routed to the same shared shadow-state handler/model — there is no separate ZS500 message handler. This was confirmed directly from the router's device-type-to-handler mapping table, where the `HPM` and `ZS500` device-type constants both map to the identical handler index.

**Credentials:** short-lived Cognito session credentials obtained through the authenticated user session (consistent with the generic AWS IoT auth pattern used by other device types in this app — see client.md for the shared login/token flow that ultimately provisions these).

## BLE Provisioning

BLE is used only for initial WiFi/network provisioning, not for ongoing communication — confirmed by the absence of any GATT read/write call sites in the home-screen or equipment-control view-models.

**Correction vs. an earlier draft of this document: ZS500 does NOT use the `"*@"` length/CRC16 frame format described further below** — that frame format is used by the robot-cleaner (VRF/VAX) and TCX BLE provisioning flows only. ZS500 uses a simpler, distinct packet format (see "ZS500 packet format" below). The two were conflated in an earlier draft because ZS500's UUID *values* are shared with the VAX device type (see table below), which led to incorrectly assuming the framing was shared too — it isn't; only the GATT UUIDs are.

### UUIDs

| UUID role | Value | Shared with |
|---|---|---|
| Profile (advertised) | `e355482b-45d9-c3a4-4d40-fee77d6f77f2` | Unique to ZS500 — the VAX profile UUID differs (`2970dc32-...`) |
| Service (GATT) | `0ad5190e-640d-4e05-9e47-2d2bb36c51e7` | Byte-for-byte identical to VAX's service UUID, and to VRF's (written uppercase in source, same value) |
| RX (named `..._RX_UUID` in source) | `f5cfc940-4341-4a3e-87f8-30c903d4dc96` | Identical value to VAX's RX UUID. **The app enables GATT indications on this UUID — it is the one the app *reads from*, not writes to.** |
| TX (named `..._TX_UUID` in source) | `0fb6258a-9206-4923-9a2d-1d2ad6ee7adb` | Identical value to VAX's TX UUID. **The app *writes* outgoing packets to this UUID.** An earlier draft of this document had the RX/TX read/write roles reversed. |

### ZS500 packet format (confirmed directly from the packet-builder/reassembly code; this is NOT the `"*@"`/CRC16 frame used by VRF/VAX/TCX)

Outbound (app → device), written to the TX UUID:

```
"##" + TOTAL_PACKETS(1 byte) + PACKET_INDEX_1_BASED(1 byte) + PAYLOAD_CHUNK(raw bytes)
```

- No CRC, no length header distinct from the single `TOTAL_PACKETS` byte.
- If the JSON payload fits within one write (MTU allows it), `TOTAL_PACKETS` and `PACKET_INDEX` are both sent as `1`.
- Otherwise the payload is split into chunks of `(MTU - 4)` bytes each, and each chunk is wrapped in its own `"##" + total + index + chunk` packet.

Inbound (device → app), delivered as GATT indications on the RX UUID and reassembled the same way: each notification's bytes `[2]` and `[3]` carry the total-packet-count and current-packet-index (not `[0]`/`[1]`, which are the literal `"##"` marker), the payload chunk starts at byte `[4]`, and chunks are concatenated until `total == current`, then parsed as JSON.

**The `$!##` acknowledgement marker described below does NOT apply to ZS500** — it is checked only in the VRF/VAX and TCX BLE flows. ZS500's "acknowledgement" is just the JSON reply itself, read from the reassembled payload's `state.reported` object (see Provisioning payloads below).

### VRF/VAX/TCX frame format (for comparison — NOT used by ZS500; confirmed directly from the frame-builder helper)

```
"*@" + LENGTH_HEX(4 hex digits, uppercase) + ONES_COMPLEMENT_OF_LENGTH_HEX(4 hex digits, uppercase) + PAYLOAD + CRC16(4 hex digits, uppercase)
```

- `LENGTH_HEX` is the hex representation of the payload string's character length (not byte length), zero-padded to 4 digits.
- The ones-complement step converts the length hex to a 16-bit binary string and flips each bit, then converts back to a zero-padded 4-digit hex string.
- `CRC16` is computed over the entire frame *up to but not including* the CRC itself (i.e. over `"*@" + lengthHex + complementHex + payload`), using a standard CRC-16/ARC-style table-driven algorithm (initial value 0, table-based, polynomial consistent with CRC-16/ARC), rendered as 4-digit uppercase hex.
- **Acknowledgement marker:** `$!##` — sent by the device to acknowledge receipt of a frame in this flow; the app checks incoming notification payloads against this exact literal. Not applicable to ZS500 (see above).

**Provisioning payloads** (sent as raw JSON for ZS500's `"##"`-packet format, or as the `PAYLOAD` portion of the `"*@"` frame above for VRF/VAX/TCX — both use the same payload strings):

| Purpose | Payload |
|---|---|
| Request serial number | `{"state":{"sn":1}}` — reply read from `state.reported.sn` |
| Request SSID list | `{"state":{"ssid":1}}` — reply read from `state.reported.ssid` |
| Send WiFi credentials | `{"state":{"wi":{"sd":"{ssid}","pw":"{password}"}}}` — reply read from `state.reported.wi.rt` (integer result code) |

## Not Observed / Needs Verification

The following items could not be confirmed from the decompiled reference source and should not be assumed:

1. Exact casing of the `aws.status` string as actually sent by a ZS500 unit on the wire. The reference matches it case-insensitively (see `aws.status` field reference above), so the app's own code doesn't pin this down either.
2. `hs` field semantics on `hp_0`.
3. `hmi.ff.pg` sub-field (`bd`, `fs`, `ts`, `te`) purposes.
4. Whether `sns_1`/`sns_2` `type`/`state` use standardized enumerations, and what their wire values are.
5. Whether `fan` is an RPM value or a boolean-like flag — the UI only checks zero vs. nonzero.
6. Catalogued `errorCode` string values and their meanings beyond `"0"` = no error.
7. Catalogued `et` (equipment type) and `md` (model) field values.
8. Whether the device ever reports temperatures in a unit other than the implied default (no unit-conversion logic was found for HPM/ZS500).
9. Whether ZS500 supports a REST-only (non-MQTT) operating mode in any other client/environment — only the Android reference app's call sites were examined. (The app itself always uses MQTT for the live home screen and REST only for the systems-list status poll and provisioning — see Real-Time Transport above — but a non-Android client/firmware mode wasn't something this research could rule out.)
10. Where the MQTT session's Cognito/static credentials are derived from server-side — only that the client uses static access-key/secret/session-token credentials with a 60s keepalive and QoS1 subscriptions was confirmed; the server-side exchange producing those credentials wasn't traced.
